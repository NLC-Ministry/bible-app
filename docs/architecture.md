# Architecture

Background reference moved out of `CLAUDE.md` (#381) so it isn't loaded into every session. `CLAUDE.md` keeps only the rules; this file keeps the full description and the history behind them. Read it before changing entry points, load order, `js/db.js`, auth, tab modules, or backend tables/Edge Functions.

## What this is

新生命聖經速讀計畫 (NewLife Bible Speed Reading) — a Traditional-Chinese PWA for a church's quarterly Bible-reading challenges: reading tracker, plans, personal/group statistics, leaderboards, gamification badges, and devotional notes. It is a **satellite app** of the NewLife Member Hub and integrates with the NLC (紟道) ecosystem SSO.

Stack: **vanilla JS, HTML, and CSS for all the main tabs — no framework, no bundler for app code in dev** (the production build runs a real `esbuild --bundle --minify` pipeline via `scripts/bundle.mjs`, not just hashing — see [Commands](../CLAUDE.md#commands)). One deliberate exception: the issue-report feature (`components/issue-report/*.tsx`, mounted via React's `createRoot` from `js/modules/issue-report-ui.js`) is a real React + TypeScript island, bundled as its own separate lazy chunk (`issue-report-ui.bundle.js`) — "no framework" does not apply to that corner of the codebase. Third-party libs: Supabase JS is pinned by a CDN `<script>` tag in `index.html`/`exam.html`/`grade.html` that the build rewrites to a same-origin copy from `vendor/` (#418); Tailwind utilities are generated at build time from `tailwind.config.cjs` into `tailwind.<hash>.css`, linked from `index.html` only (#418 — the CLI scans source, so write full class names, never `bg-${x}`); Chart.js and html2canvas are each lazy-loaded from CDN on demand by the module that needs them (`plan.js`, `home.js`) rather than declared upfront. Icons are **Lucide**, compiled at build time into `js/design/icon-registry.js` by `scripts/generate-icon-registry.mjs`. Backend is Supabase (Postgres + Edge Functions). Hosted on Vercel.


### Config generation

`config.js` is **git-ignored and generated** by `build-config.js` from `.env` (copy `.env.example` → `.env`). Never edit `config.js` by hand — it is overwritten on every build. It exposes two globals to the frontend: `SUPABASE_CONFIG` (`url`, `anonKey`) and `NLC_CONFIG` (`clientId`, `issuer`, `memberHubUrl`, `scopes`).

## Architecture

### Entry points and script loading (hybrid: legacy globals + real ES modules)

There are **four separate static HTML entry points**, each bootstrapping its own single `<script type="module">` — there is no `main.js`:
- `index.html` → `js/app.js` (the main SPA: all tabs, PWA/offline, onboarding).
- `exam.html` → `js/exam-entry.js` → mounts `js/modules/exam.js` (`mountExamRunner`).
- `grade.html` → `js/grade-entry.js` → mounts `js/modules/grading.js` (`mountGradingWorkspace`).
- `repair.html` — static cache-recovery fallback page (see `window.showAppStyleRecovery` in `index.html`).

The back-office console (#555) is **not** one of these: `admin/admin.html` → `admin/admin-entry.tsx` is a separate React + TypeScript app built by `scripts/build-admin.mjs` into `dist-admin/` and deployed as its own Vercel project (`vercel.admin.json`) on its own `vercel.app` domain. It loads none of the core chain below and talks only to the `admin-api` Edge Function — see [admin-console.md](admin-console.md). The one exception is its same-origin `/legacy` iframe (#550, `admin-legacy/legacy-entry.js`): the old admin-tab sections (plus the old plan-tab admin card, `plan-admin.js`) moved over unchanged, which **does** load the core chain (`state.js` → `db.js` → … → `admin.js`) behind `admin-legacy/globals.js` (in-memory storage, a token-from-the-console `window.auth`, the config `config.js` would set). Since #551 that markup lives in `admin-legacy/admin-view.html`, and the build swaps it in for the App's `<!-- admin-view:start/end -->` region (`scripts/lib/legacy-markup.mjs`); the member App no longer ships `admin.js`, `plan-admin.js`, `campaign-rule-editor.js` or the report-management UI at all (`scripts/bundle.test.mjs`). Changes to the core chain's load order or to the globals it expects must keep that entry building and booting too (`scripts/admin-legacy.test.mjs`, `scripts/admin-legacy-boot.test.mjs`).

Each entry script starts with a fixed, order-dependent chain of plain side-effect `import './x.js'` statements for the shared "core" files: `config.js` → `data/bible_data.js` → `data/bible_verse_counts.js` → `copy/zh-Hant.js` → `data/church_campaign.js` → `design/design-tokens.js` → `design/design-system-helpers.js` → `design/icon-registry.js` → `design/icons.js` → `state.js` → `auth.js` (+ `auth-launch.mjs`) → `db.js` → `utils.js` → `gamification.js`. This is real ES module syntax now (`type="module"`, `import`), **not** separate `<script>` tags — but `state.js`/`db.js`/`auth.js`/`utils.js`/`gamification.js` are still written pre-ESM style: they attach their API to `window` (`window.state = state`, `window.db = db`, …) instead of exporting it, and every consumer — including modules loaded much later — reads them back as bare identifiers (`state.activePlan`, `db.foo()`) or via `typeof fn === "function"` guards. This works because a module's unresolved free variables still fall through to the shared global object, same as a classic script. **The load order above is still load-bearing**: these files run once, in sequence, to populate that shared surface, and later code assumes it's already there.

Everything built more recently (`js/modules/*.mjs`, `js/data/*.mjs`, `js/pwa/*.js`) is a real ES module with proper named `export`/`import` and no `window` involved — prefer this style for new cross-file logic instead of adding another `window.foo`.

Tab views are **not** loaded eagerly at boot. `js/app.js` lazy-loads `js/modules/home.js`, `bible.js`, `plan.js`, `pastoral.js`, `profile.js`, `team-registration.js` (and helpers such as `plan-stats.js`, `exam.js`) on first use via an internal `loadModule(name)` helper (names map to literal `import()`s in `LAZY_MODULE_LOADERS`) — dynamic `import()`, retried on failure, cached in `moduleCache`, then calls the module's exported `init()`. (There is no `js/views/` directory — view/tab controllers live in `js/modules/`.) In production each is a content-hashed chunk (see [Cache-busting and updates](pwa-architecture.md#updates-and-stale-builds)), fetched only when the user first opens that tab.

### Central state

`js/state.js` defines a single global `state` object (current user, org structure, active plans, reading logs, reader state, highlights, chart instances, admin filters) plus:
- `CHURCH_PLAN_PRESETS` — the hardcoded quarterly plan definitions (books + monthly breakdown for 2026–2027).
- `appRouter` — tab/view switcher (`switchTab`, `goBack`, `updateNavigationChrome`). Views are `.view-pane` sections toggled by `.active`.
- **Hash routing (#370)**: `js/modules/hash-route.mjs` (URL format, pure functions) + `js/app-hash-routing.mjs` (wiring). The URL mirrors the current view — `#/bible`, `#/plans`, `#/plan/<globalPlanId>[/personal|stats|ranking]`, `#/profile[/<detail>]`, `#/admin[/<section>]`, no hash for home; the legacy `#my-exams` still opens the exams page. Boot opens the route (saved in sessionStorage across the Logto redirect); afterwards every `app:route-changed` event (fired by `updateNavigationChrome`, profile subpages, plan group subviews) rewrites the URL with **`replaceState` only** — no history entries are pushed, so the Android back-button order in `app.js`'s `popstate` handler is unchanged. A new view state that doesn't go through `updateNavigationChrome` must dispatch `app:route-changed` itself, or a reload won't land on it.
- Theme management (light/dark/warm) persisted to `localStorage`.
- `escapeHTML()` — use this for any user-supplied string rendered into innerHTML.

### Data layer — the dual-client shim (`js/db.js`, ~6,100 lines)

`db.js` is the entire data-access layer (grown well past its original size — budget accordingly when estimating changes here). The key design: `state.supabase` is **either** a real Supabase client **or** an `NlcDataClient` shim, chosen at runtime by login method. Both expose the same `.from(table).select().eq()...` chainable API so callers don't care which is active:

- **Google/email login (dev/localhost only):** real `@supabase/supabase-js` client, RLS-enforced.
- **NLC Logto SSO (production):** `createNlcDataClient()` returns a shim whose `NlcQueryBuilder` serializes queries to JSON and POSTs them to the `nlc-data` Edge Function, which verifies the Logto token and uses the service role. This exists because the app uses **church Logto auth, not Supabase Auth**, so RLS can't see a Supabase JWT.

When adding data access, use the `state.supabase.from(...)` builder so it works in both modes. Note the shim only implements a subset of PostgREST (`select/insert/update/delete/upsert/eq/is/in/or/order/limit/single/maybeSingle`) — a query chain that works against the real client in dev can silently misbehave through the shim in production; there's no automated check that the two stay behaviorally equivalent.

### Auth (`js/auth.js`)

Logto OIDC + PKCE client for NLC SSO. Does discovery on `issuer`, handles the redirect callback, stores tokens in `localStorage` (`nlc_*` keys), and exchanges the Logto token for a Supabase profile via the `nlc-session` Edge Function. `auth.getValidAccessToken()` transparently refreshes; `db.js` retries once on 401.

### Bible text (`js/data/bible_data.js`)

Chapter text is fetched live from public Bible APIs (bible-api.com, bolls.life) with `assertCompleteEnough()` validation (must be Chinese, not truncated to 10 verses) and a small hardcoded `BIBLE_FALLBACK` for offline/failure. `bible_verse_counts.js` holds per-chapter verse counts. `CHURCH_PLAN_PRESETS` book names are Traditional Chinese; `BOLLS_BOOK_CODES` maps English names to API codes.

### Tab modules (`js/modules/`, lazy-loaded — see above)

- `home.js` — dashboard tab: verse of the day, announcements, devotional highlights.
- `bible.js` — immersive Bible reader: highlights, TTS, font/version controls.
- `plan.js` (**~10,300 lines** — by far the largest file in the app) — plan list, plan detail, daily task checklists, admin plan CRUD, inline reader, **and** the Chart.js personal/group/admin stats & leaderboard dashboards (there is no separate `stats.js`; it's all in here).
- `pastoral.js` — the 管理 tab (#551, #570) for pastors and leaders down to group leaders (the system administrator sees the whole church): 總覽 (funnel, 需要關心 counts, next-level unit comparison — numbers only), 名單 (one row per person sorted by days behind, expanding without a request; 進度／最後打卡 conditions plus team, the same rules as the console from `_shared/progress/plan-report.mjs`; 提醒加入 and 關心提醒), 團隊, 測驗 (participation only, no ranking). Data comes from `nlc-data`'s leader `plan_summary` (fetched per scope) and `plan_roster` (fetched once when a roster/teams/quiz tab opens, audited as `view_plan_roster`) via the shim's `planReport()`; the scope is decided by the server (`getVisibleProfileIds`). The App has no CSV export — exports are server-generated and audited in the console. Leader care reminders go through `send_care_reminder` (one per sender/recipient/plan/day, #574) and are audited as `care_reminder.send`. System-management features are not in the App: old `#/admin/<system section>` links send the administrator to the console (`ADMIN_CONSOLE_SECTION_ROUTES` in `js/admin-console-link.mjs`), and 個人頁 has an admin-only 「開啟管理後台」 row.
- `admin.js` (~4,300 lines) — the old admin tab. Only the console's legacy iframe loads it (see above); the member App never does.
- `profile.js` — account settings, badge wall.
- `team-registration.js` — team join/switch flows.
- `exam.js` / `grading.js` — mounted from the standalone `exam.html` / `grade.html` entry points, not from `app.js`.

## Backend (`supabase/`)

- **Active schema:** `supabase/migrations/` starting at `0001_clean_schema.sql`, now past **180+ migrations**. Core tables: `profiles` (stable user record), `user_identities` (links login methods → one profile), `reading_plans`, `reading_logs`, `devotional_notes`, `global_plans`, `church_announcements`, and org tables (`great_regions`, `pastoral_zones`, `small_groups`). RLS resolves the caller via `current_profile_id()`. This list is **not exhaustive** — three substantial feature areas each have their own table cluster that predates none of this doc's other sections but has never been added here either: reading teams (`reading_teams`, `reading_team_members`), the exam/大測驗 system (`exam_papers`, `exam_attempts`, `exam_grading_assignments`), and the issue-report conversation threads (`issue_reports`, `issue_report_messages`).
- **Personal plans (#473):** a `reading_plans` row with `is_personal = true` is a plan the member created for themselves (no `global_plan_id`/`preset_key`, enforced by a CHECK). Identify them only by this flag — legacy preset enrollments also have both ids empty. Trigger `enforce_personal_plan_rules` caps each member at 5 active ones (`end_date` ≥ Taipei today), keeps the flag immutable, and locks books/dates after the first reading log. They never count toward leaderboards, teams, or church statistics: any new SQL function that reads `reading_plans`/`reading_logs` must either filter by a church plan's `global_plan_id`, stay within the caller's own rows, or exclude `is_personal` — `scripts/personal-plans.test.mjs` fails until it is classified there. Rules and form validation live in `js/data/personal-plans.mjs`.
- **Admin audit log (#549):** `audit.admin_events` lives in its own `audit` schema, which the API never exposes; no API role (not even `service_role`) has table privileges. The only writer is `audit.record()` (service_role only); triggers block UPDATE/DELETE/TRUNCATE except the weekly retention purge `audit.purge_expired()` (1 year, pg_cron `audit-admin-events-weekly-purge`). `admin-api` (#547) calls `audit.record()` inside the same transaction as each change; `nlc-data`'s legacy admin writes (admin tables, the RPCs in `AUDITED_ADMIN_RPCS` in `supabase/functions/nlc-data/admin-audit.ts`, refused admin calls) add a best-effort row afterwards through `public.record_admin_audit_event()`. Members' own writes are not logged. A new admin RPC that changes data must be added to `AUDITED_ADMIN_RPCS` (`scripts/admin-audit.test.mjs` fails otherwise).
- **Request ids and report diagnostics (#548):** every frontend `nlc-data` call goes through `fetchNlcTracked()` (`js/diagnostics/report-diagnostics.mjs`), which sends `x-request-id` and keeps the last 20 calls in memory; `nlc-data` echoes the id in the `x-request-id` response header and logs one `nlc_data_request` JSON line per request. Issue reports carry `metadata.diagnostics` (redacted, ≤ 8 KB); on insert `nlc-data` keeps only that key (`sanitizeReportInsertPayload`). A new direct `fetch` to `nlc-data` must use `fetchNlcTracked` (`scripts/report-diagnostics.test.mjs` counts them).
- **Branch workflow (since 2026-09-27): work reaches `staging` through task branches, release via a reviewed PR.** Day-to-day changes go on a local `task/*` branch and reach `staging` through the integrator (see [Parallel tasks and integration](../CLAUDE.md#parallel-tasks-and-integration-read-before-committing-merging-or-pushing)); `staging` deploys to https://bible-speed-reading-staging.vercel.app against the staging database. Never force-push it, and never push to `main` directly. To release, open a PR `staging` → `main` (template: `.github/pull_request_template.md`, written as plain "open this page → you should see this" steps for a non-technical reviewer). **The maintainer merging that PR is the approval** — they check the staging site first; never merge a release PR yourself. `release-gate` checks the source is `staging`/`hotfix/*` and includes every non-merge commit on `main`, and `ci.yml`'s deploy job refuses to deploy a `main` commit that didn't come from a merged PR from `staging` or `hotfix/*`. Merge with a merge commit, not squash. After every release — and every hotfix — merge `main` back into `staging` (integrate skill step 9) so `main` never stays ahead. Production hotfixes: `hotfix/*` off `main` → PR to `main` → then merge `main` back into `staging`. See `docs/staging.md`.
- **Two environments, CLI-managed migrations.** Production is `ztozevcqkfrohgjmngcj`; staging is a Supabase branch, `dbtjsljrytzonjvclgrd` (see `docs/staging.md`). Since 2026-09-25 migrations are applied with the Supabase CLI instead of being pasted into the SQL Editor: `0001`–`0214` are marked applied in both projects' `supabase_migrations.schema_migrations`, and `20260925071804_branch_baseline.sql` is a no-op placeholder for the version Supabase wrote when the branch was created. **New migrations must use a timestamp name** — create them with `npx supabase migration new <name>`; a new `0215_…` file is rejected by `db push` ("inserted before the last migration on remote") and by `scripts/migration-naming.test.mjs`. Apply to staging, verify, then production, always with an explicit `--project-ref` (never rely on `supabase link`):
  ```bash
  npx supabase db push --linked --project-ref dbtjsljrytzonjvclgrd --dry-run   # staging: check what will run
  npx supabase db push --linked --project-ref dbtjsljrytzonjvclgrd
  npx supabase db push --linked --project-ref ztozevcqkfrohgjmngcj --dry-run   # then production
  npx supabase db push --linked --project-ref ztozevcqkfrohgjmngcj
  node scripts/compare-env-snapshots.mjs --run                                 # both environments still match
  ```
  Never pass `--include-all` to production. The CLI doesn't know about ordering requirements written in a migration's header (e.g. "set Vault `project_url` first" in `0212`) — read the header before pushing.
- `supabase/migrations_legacy/` — old test-period migrations, kept for reference only. Do not replay on a fresh project. (There's also a single stray file under `supabase/migrations/legacy/` — a one-off migration deliberately pulled out of the active numbered sequence; unrelated to `migrations_legacy/` despite the name.)
- **Edge Functions** (`supabase/functions/`): eight in total.
  - `nlc-session` (verifies Logto token, upserts profile/identity with service role) and `nlc-data` (per-request Logto verification + server-side table/action allowlist, then service-role DB access) — the two the app calls directly from the client. **Until 2026-09-24 neither actually verified JWT signatures** (they only base64-decoded the payload, and `nlc-session` linked accounts by email from an unverified `id_token`). Both (and `admin-api`) now embed an identical `logto-jwt-verify` block (JWKS signature + `iss` + `exp`), rolled out via `NLC_JWT_VERIFY_MODE` (`report` → `enforce`; since #564 an unset or unknown value means `enforce`) — see `supabase/functions/README.md`. Never trust a decoded-but-unverified token claim for identity again; `scripts/logto-jwt-verify.test.mjs` guards this.
  - `admin-api` (#547) — the back-office API, used only by the admin console (#555), never by the member app. One `admin_api_*` SQL function per action (service_role only); actions that change data (the report inbox, #550: reply, internal note, status, attachment/report delete; accounts, #550: managed scopes via `set_profile_managed_scopes` — roles stay read-only, they come from the Member Hub sync) write their audit row inside that same function, and actions that also touch Storage or build a CSV chain steps through `run` in `policy.ts` (`reports.ts`, `accounts.ts`, `audit.ts`, `exports.ts` — exports are generated server-side). The audit log itself (`audit_list`/`audit_event`, #550) is read through admin-api only; reading it is not audited, exporting it is. Always requires a verified Logto token (ignores `NLC_JWT_VERIFY_MODE`) whose `client_id` is in `ADMIN_API_ALLOWED_CLIENT_IDS` (unset → everything is refused). Roles come from the database; `supabase/functions/admin-api/policy.ts` maps role → capabilities, deny by default (only `admin` has any). Per-actor rate limits are counted in `admin_api_rate_limits`; `user_summary`/`reveal_pii` write `view_user`/`reveal_pii` to `audit.admin_events` in the same transaction, and refusals are recorded as `denied`. Plan progress is returned as raw counts — lag/lead is computed client-side with `js/data/schedule-progress.mjs` so the church-schedule rule stays in one place. The exception is `plan_summary`/`plan_roster` (#564, `plans.ts`, capability `plans.read`): they compute each person's status on the server by executing the shared `_shared/progress` modules — the same files the App runs — on facts from `admin_api_plan_people` (whole church, after `admin_api_assert_admin` re-checks the actor in SQL). The summary carries numbers only and is not audited; opening the roster records `view_plan_roster`. SQL also returns an independent count (`meta`); a mismatch comes back as `meta.consistent: false`. `nlc-data` serves the same two actions for leaders (`nlc-data/plan-report.ts`, scope from `getVisibleProfileIds` only, via `get_pastoral_overview`). The console's plan area (#565) adds `plan_options`, `plan_quiz` (numbers only), `plan_roster_export` (the server re-applies the console's roster filters from the same `plan-report.mjs`, no email, audited as `export`) and `care_remind` (capability `plans.remind`; one reminder per sender/recipient/plan/day, audited in the same SQL function). A new action must be added to `ADMIN_ACTIONS` with its capabilities and rate limit (`scripts/admin-api.test.mjs`).
  - **Shared code** (`supabase/functions/_shared/progress/*.mjs`, #564): the plan-progress rules (behind/ahead, last check-in, needs care), the church's canonical schedule (`church-campaign.mjs`, `plan-schedule.mjs`) and a copy of the 66-book chapter table (`bible-chapters.mjs`, parity-tested against `bible_data.js`). Plain ES modules that import only each other — the App imports them through `js/data/*` and `js/modules/pastoral-metrics.mjs`, `admin-api` and `nlc-data` import them directly. The Supabase CLI deploy follows relative imports and uploads `_shared/` with each function (`scripts/edge-function-deploy-graph.test.mjs` replays its file walk); a deploy that uploads only the function's own folder fails with `Module not found`. Changing these files means redeploying both functions and rebuilding the App.

Guarded by a shared-secret header (`x-maintenance-secret`), not a Logto/Supabase token. Needs its own Vault secret, `issue_report_maintenance_cron_secret`, matching the Edge Function's `ISSUE_REPORT_MAINTENANCE_SECRET`. Deployed and manually verified working 2026-09-16 (`SELECT public.invoke_issue_report_maintenance(FALSE);` → `net._http_response` returned `200 {"ok":true,"autoclosed":4}` — 4 stale threads got closed on the very first real run, confirming this genuinely had never executed before).

  - All of them have `verify_jwt = false` in `supabase/config.toml` because their real bearer is a Logto token or a custom shared secret, not a Supabase JWT. A Dashboard-only toggle drifts back to `true` on the next CLI deploy that doesn't know about it (this silently 401'd the since-removed `sync-devotion-video` for weeks). - The `profiles`/`user_identities` split is intentional: it prevents data loss when a user switches login method (e.g. Google → NLC Logto). First admin is promoted manually via SQL (see `supabase/README_clean_setup.md`).
- **New SQL functions default to PUBLIC-executable — revoke explicitly in the same migration, every time.** Postgres grants `EXECUTE` on every newly created function to the `PUBLIC` pseudo-role by default, and `anon` inherits it *transitively* through that — `REVOKE EXECUTE ... FROM anon` alone is a no-op against a `PUBLIC` grant. This exact gap let ~29 functions stay silently anon-callable through two cleanup attempts (`0173`, `0177`) before a third, broader sweep (`0182_revoke_public_function_execute_sweep3.sql`) finally caught them by checking `has_function_privilege('anon', ..., 'EXECUTE')` instead of trusting a role-specific grant list. Don't rely on the next periodic sweep to catch it again — every `CREATE FUNCTION`/`CREATE OR REPLACE FUNCTION` in a new migration must be followed immediately by an explicit grant:
  ```sql
  CREATE OR REPLACE FUNCTION public.some_new_fn(...) ... AS $$ ... $$;
  REVOKE ALL ON FUNCTION public.some_new_fn(...) FROM PUBLIC, anon, authenticated;
  GRANT EXECUTE ON FUNCTION public.some_new_fn(...) TO authenticated, service_role; -- drop authenticated (service_role only) if it must never be called directly by a client
  ```
  **`FROM PUBLIC` alone is not enough.** Supabase's default privileges (`ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public GRANT ALL ON FUNCTIONS TO anon, authenticated, service_role`) grant every new function **directly** to `anon` and `authenticated`, which a PUBLIC revoke doesn't touch. That let `schedule_announcement` — no caller check, so anyone with the public anon key could post a published announcement to every member — become anon-callable **twice**: `0187` fixed the 5-arg version, then `0195` added a 7-arg overload that picked the direct grant up again. `0214_revoke_anon_function_execute.sql` revoked all 24 anon-executable functions and changed the default privileges so new functions are granted to `service_role` only; it ends with a check that fails if any `public` function is still anon-executable. Grant `authenticated` explicitly when a function needs it — including any function an RLS policy `TO authenticated` calls (e.g. `profile_matches_announcement_scope`). Verify with `has_function_privilege('anon', p.oid, 'EXECUTE')`, never by reading the grant statements.
  If the function is `SECURITY DEFINER` and performs a privileged mutation (i.e. it bypasses RLS), do **not** grant `authenticated` unless the function is genuinely meant to be invoked directly by the client — granting `authenticated` on a `SECURITY DEFINER` function that expects to only ever be reached through `nlc-data`'s allowlist/`applyForcedScope` is exactly the "direct RPC bypass" vulnerability shape already fixed more than once (`d317a12`, `485679a`, `bc09eff`). Default to `service_role`-only for those.
