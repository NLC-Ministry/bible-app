## 需求

在「系統管理 → 組員總覽」加入一張圖，顯示各進度各有幾人：
讀 0 章（未讀）幾人、讀 1 章幾人、讀 2 章幾人……

## 現況（已查證）

- 「組員總覽」分頁（`js/modules/admin.js` `ADMIN_SECTIONS` id `members`）對應 `index.html` 的 `#admin-section-members`。
  它沒有自己的內容：`mountPlanManagementSections()` 會把 `#member-list-container`（參與者總覽卡片）搬進 `#admin-plan-participants-slot`。
- `renderGroupParticipantsRankingTable()`（`js/modules/plan.js`）已經為目前範圍內的每位組員算好：
  - `completed`：本計畫已讀章數，以 `book_chapter_round` 去重，**第二遍以上會累加**
  - `isNotStarted`、`isBehind`、`statusStr`（未開始／落後 N 天／今日未完成／在進度上／超前 N 天／第一遍完成／第 N 遍…）
  - 結果存在 `window._grpScopedProcessedMembers`，已套用權限範圍與大區／牧區／小組篩選
- `db.fetchMergedUsersList(planKey)` 只回傳**已加入此計畫**的人（`if (filterPresetKey && !uPlan) return null`），
  所以「0 章」＝已加入但尚未讀，不包含沒加入計畫的人。
- `renderOrUpdateChart(key, canvas, config)` 會自動延遲載入 Chart.js，重複呼叫只更新、不重建。
- **不需要新增任何 DB 查詢或 migration。**

## 與主流 APP 比較

| 產品 | 帶領者／老師看進度的做法 | 可借鏡的地方 |
|---|---|---|
| Microsoft Teams Education Insights／Reading Progress | 依狀態分組的長條，點一下列出那一組的學生 | 點圖 → 篩出名單，直接能關懷 |
| Google Classroom、Canvas | 每份作業顯示「已繳／未繳／遲交」人數 | 相對「應完成」的狀態比絕對數字好行動 |
| Khan Academy 教師端 | 一條依熟練度分段上色的堆疊橫條＋各段人數 | 一眼看全貌的摘要條 |
| Coursera 講師端 | 依單元（module）完成數畫漏斗／直方圖 | 按有意義的單位分組，不按最細的顆粒 |
| Strava、Garmin | 分布圖上標出「你在這裡」或基準線 | 參考線讓圖立刻有意義 |
| YouVersion「和朋友一起讀」 | 每位朋友讀到第幾天，沒有整體分布圖 | 單純的人數分布不常見，常搭配狀態使用 |

### 比較結論

原方案能回答「各進度幾人」，但主流做法一致多做了兩件事，讓帶領者看完圖**知道要關心誰**：

1. **標出「今天應讀到第 X 章」的參考線**，長條依相對位置上色：落後（紅）／在進度（品牌色）／超前（綠）。
   不然組長看到「讀 12 章：5 人」，無法判斷好壞。`expectedDaysCount` 與 `baselineScheduleDays` 已經有了，換算成應讀章數不需要新資料。
2. **點長條就篩選下方名單**，只顯示那個進度的人。帶領者從圖直接到關懷名單（名單已有「提醒」按鈕）。

可選的第三件事：

3. **圖上方加一條狀態摘要**（堆疊橫條或 5 個數字）：未開始／落後／今日未完成／在進度上／超前・完成。
   直接沿用每位組員已有的 `statusStr`，和下方表格的進度狀態欄完全一致。

評估後不採用的：

- **真正的時間趨勢圖**（例如每天「在進度上」的人數變化）：要用所有人的 `read_at` 回推每一天，計算量和資料量都大很多，主流 LMS 也少見。先不做。
- **改成按「計畫第 N 天」或書卷分組**：雖然比較貼近進度，但你明確要求按章數；改用參考線與上色就能取得同樣的判讀效果。

## 定案規格

### 畫面：組員總覽中，參與者總覽上方的「進度分布」卡片

1. **模式切換**：標題旁的兩段切換鈕「第一遍｜全部遍數」。預設為「第一遍」。上次選的模式存在瀏覽器 `localStorage`，讀寫都包 try/catch；讀不到時就用預設。
2. **狀態摘要條**：一排可以點的區塊，各自顯示人數。內容依模式而定，見下表。
3. **進度分布長條圖**：X 軸為章數，Y 軸為人數。「0 章」固定單獨一根。
4. **點擊篩選**：點長條或摘要區塊，下方名單只顯示那一組的人，並出現「目前篩選：讀 6–10 章（12 人）✕」。點 ✕ 或再點同一塊就取消。
   以下情況會自動清除篩選：切換大區／牧區／小組篩選、按「更新」、切換模式。

### 兩種模式

| | 第一遍模式（預設） | 全部遍數模式 |
|---|---|---|
| 要回答的問題 | 第一遍誰落後、要關心誰 | 全體整季讀到哪裡、各遍各有幾人 |
| X 軸 | 第一遍章數：0 到 N（N＝計畫總章數） | 各遍累計章數：0 到 N × 資料中的最高遍數 |
| 參考線 | 虛線，標「今天應讀到 X 章」 | 每遍的分界線，標「第一遍完成」「第二遍完成」… |
| 長條顏色 | 未讀灰／落後紅／在進度上品牌色／超前・完成綠 | 依遍數用品牌色系由淺到深，0 章為灰 |
| 最後一根 | 「第一遍已完成」，第二遍以上的人都在這根 | 沒有，第二遍以上的人照累計章數分散開 |
| 摘要條 | 未開始／落後／今日未完成／在進度上／超前・完成 | 未開始／第 1 遍中／第 2 遍中／…（有幾遍就幾格） |

- 全部遍數模式不標落後或超前。這跟 `getPlanProgressStatus` 一致：只有第一遍判斷落後或超前，第二遍以後只顯示「第 N 遍完成 xx%」。
- 在全部遍數模式下，如果還沒有人進入第二遍，圖照樣畫，並加一行「目前沒有人進入第二遍」。

### 計算規則

- **第一遍模式**
  - 第一遍已完成的人放在「完成」那根，判斷條件：`current_round > 1`，或第一遍進度 ≥ 100%，或自己的計畫 `isPlanCompleted`。
  - 其他人的章數取 `min(completed, N)`。
- **全部遍數模式**：直接用 `completed`，也就是各遍加總、同一章同一遍只算一次。例如計畫有 90 章，第二遍讀到 30 章的人是 120 章。
- **今天應讀章數**：教會原始日程（`baselineScheduleDays`）中，已經過的日子的章數加總。
- **超前門檻**：再多讀完下一個有章節的日子，才算超前。這跟表格用 `countExactDaysCoveredByChapters` 判斷「超前 N 天」的方式一致，所以圖的顏色和表格的進度狀態會相同。
- **長條合併**：長條數超過上限時（手機約 30 根、桌機約 60 根），依序改用每 5、10、20、50 章一組，選第一個不超過上限的組距。「0 章」永遠單獨一根。全部遍數模式下，每遍的分界必須落在兩組之間，不能切在某一組中間。
- **長條上色**
  - 整組都在「今天應讀章數」之前：落後。
  - 整組都在超前門檻之後：超前。
  - 其他：在進度上。
- **摘要條**：分類直接沿用每位組員的狀態欄位（`statusKey`），與表格的「進度狀態」欄一致。
- **範圍**：跟大區／牧區／小組篩選連動，不跟姓名搜尋連動。已知限制：如果重新整理時搜尋框裡已經有字，圖表會保留上一次的結果，不重算，以免改動現有的搜尋行為。

### 查證結果：章數範圍（2026-09-23，已處理）

**問題**：自己的章數（`myPlanReadCount`）只算 `plan.days` 裡的章節；別人的 `chapters_read`（`db.js` `_executeFetchMergedUsersList`）只用 `plan_id` 篩選，**沒有檢查書卷**。本遍進度 % 也一樣。

**寫入路徑**：`db.logChapterRead()` 有 4 個呼叫處。其中 3 處的章節來自計畫本身。第 4 處是 `bible.js` 讀經頁的「標記已讀」按鈕，它會把正在看的任何一章記到目前的計畫上；但 `#mark-read-btn` 已經不在 `index.html` 裡，所以不會執行。現在的程式不會寫出計畫外的紀錄。

**實際資料**：用 SQL 查出 1 個人、5 筆計畫外的紀錄。都在 `church_r1final_2026_09`（9 月出埃及記），內容是民數記 16–20 章第 1 遍，打卡時間是 2026-09-01 21:23–21:41（台灣）。

**原因**：`0142` 月度拆分沒有建立新的計畫紀錄，而是把組員原本第二階段那筆 enrollment（同一個 id）直接改指到 9 月計畫。`0142` 結尾的檢查會擋下任何非出埃及記的紀錄，所以這 5 筆一定是 migration 跑完之後才寫進來的：這位組員當時開著舊版 App，看到的仍是舊第二階段（出到申）的日程，提前讀了民數記。這是部署過渡期的一次性事件。

**處理**：
- 前端防線（已實作）：`js/data/current-round-progress.mjs` 新增 `filterLogsToPlanBooks()`。`fetchMergedUsersList` 算別人的 `chapters_read` 和本遍進度前，會先過濾掉計畫書卷以外的紀錄；書卷清單用 enrollment 的 `target_books`，沒有的話退回對應 global plan 的 `books`，兩者都沒有就不過濾。測試在 `scripts/plan-scope-log-filter.test.mjs`。
- 這 5 筆資料：決定刪除，由使用者在 Supabase SQL Editor 執行。
- 伺服器端檢查（`nlc-data` 或 trigger 擋掉計畫外書卷的寫入）：暫不做。

**尚未涵蓋**：伺服器端的排行 RPC（例如 `get_reading_team_leaderboards`）的 `chapters_read` 是在 SQL 裡計算的，也沒有限定書卷。刪掉這 5 筆之後目前不受影響，但如果以後再出現類似資料，那邊不會自動排除。
